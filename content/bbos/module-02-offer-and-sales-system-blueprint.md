# Module 2 — Offer and Sales System · Production Blueprint (Revision 2, Approved)

**Status:** Architecture approved. This is a design/production blueprint only — **not** Module 2 prose.
**Canonical title:** **Offer and Sales System** (use in body copy, governance documents, headings, and cross-references). Use "Offer & Sales System" (ampersand) only on covers or compact display surfaces.
**Design authority:** Product Constitution §7 (M2 outcome), §8 (journey Weeks 3 and 7), §9 (scope control), §11 (Maya). **Editorial authority:** BBOS Editorial & Design Style Guide (voice §1, terminology §4, callouts §9, worksheet §10, spreadsheet §11, accessibility §14, action/milestone standard §3).

## 1. Purpose

Module 2 turns the loose set of services the owner named in Module 1 into **one clear, packaged offer** and gives them a **visible pipeline** so no lead or opportunity is lost in their head. It replaces "I sort of sell a few things and follow up when I remember" with "I have a defined core offer, a simple ladder around it, and a system that shows me exactly where every opportunity stands and what to do next."

Module 2 is deliberately **structure, not price**. It defines *what* is sold and *how opportunities are tracked and followed up*. Setting the actual numbers is Module 3's job. **This boundary is the module's single most important scope rule.**

## 2. Customer transformation

- **Before (entry state):** Services are a vague menu. The owner quotes ad hoc, follows up inconsistently, and cannot see how many live opportunities exist or which are close to closing. Selling feels like reacting.
- **After (exit state):** The owner has a written, packaged **core offer** with a simple **Offer Ladder**, a publishable **Offer One-Pager**, and a **visible pipeline** (Lead → Qualified → Proposed → Won / Lost) with a written **Follow-Up Cadence** and a reusable **"Should I Say Yes?"** qualification filter. Selling becomes a repeatable process with visible outputs, not a mood.
- **Emotional shift:** from "I hope work shows up" to "I can see my opportunities and I know my next action for each one." (Stated as control and clarity — never as guaranteed revenue.)

## 3. Learning objectives

By the end of Module 2 the owner can:

1. Package their Module 1 core offer into a clearly defined offer with **Included / Optional / Not Included** boundaries.
2. Build a simple 3-rung **Offer Ladder** (entry / core / premium) without setting prices yet.
3. Produce a publishable **Offer One-Pager** for their ideal customer.
4. Set up a **visible pipeline** using the four canonical stages.
5. Sort current real opportunities into the pipeline.
6. Apply the **"Should I Say Yes?"** filter to qualify or decline opportunities on fit, capacity, and standards — before they consume time.
7. Write and commit to a **Follow-Up Cadence** (trigger → action → timing) for active leads.
8. Explain how the pipeline will be maintained inside the Weekly Operating Rhythm (Module 4) — without building the rhythm here.

## 4. Chapter architecture

Five chapters; each leads to a visible output (Style Guide §3 as amended). Chapters 2.1–2.3 build the **offer**; 2.4–2.5 build the **sales system** (pipeline + qualification + follow-up).

| # | Chapter | Core action → visible output |
|---|---------|------------------------------|
| 2.1 | **From Services to a Structured Offer** | Package the offer with **Included / Optional / Not Included** → completed Offer Builder |
| 2.2 | **The Offer Ladder** | Define entry / core / premium rungs (no prices) → filled Offer Ladder |
| 2.3 | **The Offer One-Pager** | Build the publishable one-pager (shows the 3 boundary tiers) → completed Offer One-Pager |
| 2.4 | **The Visible Pipeline & Qualifying** | Set up the 4-stage pipeline **+ apply "Should I Say Yes?" at the Lead → Qualified gate** → populated pipeline with logged decisions |
| 2.5 | **The Follow-Up Cadence** | Write trigger → action → timing rules → written Follow-Up Cadence |

The "Should I Say Yes?" framework lives inside Chapter 2.4 (rather than adding a chapter) to keep the module lean. Chapter 2.5 closes with a short bridge into Module 3.

## 5. Key frameworks

1. **The Offer Builder (five fields).** Packages one offer so it can be delivered the same way each time and priced cleanly in Module 3:
   - **Who it is for** — the ideal customer (from Module 1).
   - **Intended outcome** — the real job the offer delivers (from Module 1's "business you're really in").
   - **Included** — the standard scope always delivered with the offer.
   - **Optional** — named add-ons the customer can choose. **Unpriced in Module 2**; each becomes its own price line in Module 3.
   - **Not Included** — explicit exclusions that prevent scope creep and set expectations up front.
2. **The Offer Ladder.** Three rungs — **entry** (low-commitment first step), **core** (the main offer from Module 1), **premium** (a fuller or recurring version). Structure only; each rung carries a clearly labeled "price — set in Module 3" placeholder.
3. **The Visible Pipeline.** Canonical stages **Lead → Qualified → Proposed → Won / Lost** (fixed names, Style Guide §4), each with a one-line "entry test" for moving an opportunity forward.
4. **"Should I Say Yes?" qualification filter (applied at Lead → Qualified).** A fast, reusable decision gate the owner runs on each new opportunity or scope-creep request. Five checks:
   - **Fit** — is this my ideal customer, and does it match my core offer/ladder? *(from Module 1)*
   - **Boundary** — is the request **Included**, **Optional**, or **Not Included**? *(uses the Offer Builder tiers)*
   - **Capacity** — can I deliver it well without harming current commitments?
   - **Margin-viable** — can it be delivered inside my offer and priced to my target margin? **Yes/no feasibility only — Module 2 must not calculate or suggest a price; the number is set in Module 3.**
   - **Red flags** — any poor-fit signals (chronic late payment, chaos, discount pressure, endless scope creep)? *(from Module 1's poor-fit definition)*

   **Output (exactly one):** **Yes** (advance to Qualified) · **Not now** (park with a reason + revisit date) · **No** (decline respectfully). **Each decision includes a one-line reason.**
5. **The Follow-Up Cadence.** A small rule table — *trigger → action → timing* (e.g., new Lead → send intro + one qualifying question → within 24h). Applies to **active leads/opportunities only.** Following up **past customers** for repeat business or referrals is **Module 7** (hard boundary).

Principle mapping (Style Guide voice; Constitution §4): Fit/Red flags → Integrity & Service; Boundary → Excellence; Capacity → Sustainability; Margin-viable → Profitability. Frameworks are decision filters, not slogans.

## 6. Worksheets required

- **Offer Builder worksheet** — one per offer; fillable fields: *Who it is for · Intended outcome · Included · Optional · Not Included.* (Style Guide §10 layout.)
- **Offer Ladder worksheet** — three-rung grid with a labeled "price — set in Module 3" field on each rung.
- **Offer One-Pager** *(companion asset — see §12)* — displays the Included / Optional / Not Included tiers; doubles as the Chapter 2.3 output.
- **Pipeline Tracker** — the four-stage board/table, delivered as the **pipeline section of the Weekly Operating Rhythm workbook** (Constitution Week 3), not a new standalone asset.
- **"Should I Say Yes?" Qualification Gate** — a short reusable checklist **folded into the Pipeline Tracker** (a checklist section, not a calculator; no new required asset).
- **Follow-Up Cadence planner** — trigger → action → timing table; lives in the Rhythm workbook alongside the pipeline.

All worksheets: grayscale-legible, fillable fields, one job per sheet, footer "Supports Module 2."

## 7. Calculator requirements

**None new for V1.** Scope-control decision (Constitution §9 excludes complex dashboards; the only V1 calculators are Pricing & Margin in Module 3 and Cash-Flow & Runway in Module 5).

- The pipeline is a **visible tracker**, not a forecasting calculator. A simple manual count of opportunities per stage inside the Rhythm workbook is sufficient.
- **Do not** build a "pipeline value / revenue forecast" calculator — it would introduce projected-income figures (income-promise risk) and duplicate Module 5. If a per-stage tally is wanted, it stays a plain count with a Note that it is not a revenue forecast.

## 8. Examples required

Running example: **Maya's Property Services** (Constitution §11). All figures fictional, labeled, and **price-free** (pricing deferred to Module 3).

- **2.1 — Offer Builder (three tiers):** *Who:* short-term rental hosts / small property managers with 2–5 properties. *Outcome:* properties consistently guest-ready on time. *Included:* standard turnover (kitchen, bath, floors, linens reset, guest-ready check). *Optional:* inside-oven/fridge deep clean, laundry service, consumables restock. *Not Included:* repairs, moving heavy furniture, yard/outdoor work.
- **2.2 — Offer Ladder:** *Entry:* one-time trial turnover or deep clean. *Core:* scheduled turnovers. *Premium:* recurring multi-property weekly support. Prices shown as "[price — set in Module 3]".
- **2.3 — Offer One-Pager:** Maya's compact, filled one-pager (worksheet-ready, like the Module 1 Snapshot example), showing the three boundary tiers.
- **2.4 — Pipeline + "Should I Say Yes?":** Maya sorts 3–4 fictional opportunities across the four stages (e.g., the property manager from her Module 1 audit sits in "Qualified"). She runs the filter on two: the "come today for cheap" one-off = **No** (fails Fit + Red flags: discount pressure); the property manager wanting weekly service = **Yes → Qualified**. Each decision logged with a one-line reason.
- **2.5 — Follow-Up Cadence:** Maya's 2–3 trigger → action → timing rows.

**Critical example rule:** no prices and no earnings anywhere in Module 2 examples. Use "[price — set in Module 3]" placeholders so examples stay consistent when Module 3 fills them in.

## 9. Callout types (canonical five only — Style Guide §9)

- **Do This Now** — the immediate action per chapter (e.g., "Sort every current opportunity into a stage now").
- **Example** — the Maya blocks above.
- **Warning** — common failure modes: menu creep, discounting to win, treating follow-up as pestering, using the pipeline as a to-do dump, saying yes to poor-fit work.
- **Tip** — e.g., "One offer, defined well, beats five vague ones."
- **Note** — scope/non-advice reminders: pricing is Module 3; pipeline counts are not revenue forecasts; no income promise.

Layout discipline: max two callouts per page.

## 10. Exercises (one per chapter; each produces a visible output)

- **Ex 2.1** Package your core offer with Included / Optional / Not Included (Offer Builder).
- **Ex 2.2** Build your Offer Ladder — 3 rungs, no prices.
- **Ex 2.3** Create your Offer One-Pager.
- **Ex 2.4** Set up your pipeline; apply **"Should I Say Yes?"** to every current opportunity; sort and log each into a stage with a one-line decision reason.
- **Ex 2.5** Write your Follow-Up Cadence and commit it to your Weekly Operating Rhythm (forward reference to Module 4).

## 11. Completion milestone (one formal module milestone — Style Guide §3)

Module 2 is complete when the owner can point to:

- A **packaged core offer** with Included / Optional / Not Included (Offer Builder complete).
- A **3-rung Offer Ladder** (prices intentionally deferred to Module 3).
- A **published Offer One-Pager**.
- A **visible pipeline** with all current opportunities sorted into Lead / Qualified / Proposed / Won / Lost.
- A used **"Should I Say Yes?"** filter with logged Yes / Not now / No decisions.
- A **written Follow-Up Cadence** for active leads.

Followed by a single **module completion checklist** (no per-chapter micro-milestones).

## 12. Required companion assets

- **Offer One-Pager** — Constitution §9 required asset; primary Module 2 deliverable (Week 7). Displays the three boundary tiers.
- **Weekly Operating Rhythm workbook (pipeline · qualification gate · follow-up sections)** — Constitution §9 required workbook; Module 2 uses/populates these sections (Week 3). Built once, shared with Module 4.
- **Client proposal template** — Constitution §9 required asset, but its build belongs to the "Proposed" stage work later (journey Week 11, Modules 6/7). Module 2 **references** it at the "Proposed" pipeline stage; it is **not** built here.

**No new required companion asset or calculator is introduced** (scope discipline). The "Should I Say Yes?" Qualification Gate is a checklist section within the existing Rhythm workbook.

## 13. Dependencies FROM Module 1

- **One-Page Business Snapshot** → supplies the **core offer** (packaged in 2.1) and **ideal customer / poor-fit** (targets the One-Pager and powers "Should I Say Yes?").
- **"Business you're really in" sentence** → the headline/outcome line of the Offer One-Pager and the Offer Builder's Intended outcome.
- **Owner's Time Map "Selling" bucket** → motivates the Follow-Up Cadence (make selling a system, not a scramble).
- **First weakness to fix** → if the owner's first weakness was follow-up or offer clarity, Module 2 is where it gets addressed; reference, don't restate.

**Handling rule:** *reference* Module 1 outputs; do **not** re-teach ideal customer / core offer (repetition risk, §16).

## 14. Dependencies INTO Module 3 (Pricing With Dignity)

- The **packaged offer** and **Offer Ladder** are exactly what Module 3 prices via **Cost Stack → Target Margin → Price**. Module 2 leaves clean, labeled price placeholders on the ladder, the Optional items, and the one-pager.
- The **"Proposed" pipeline stage** needs a price to exist — so Module 2 explicitly defers the number to Module 3 and notes that proposals become "real" once Module 3 pricing is set.
- The **Margin-viable** check in "Should I Say Yes?" is a yes/no feasibility gate in Module 2; the actual target margin and price are defined in Module 3.
- **Handoff line (near the Module 2 close):** the structured offer goes into Module 3 to be priced with dignity.

## 17. Editorial risks

1. **Pricing bleed (highest risk):** Module 2 drifting into setting prices/margins → collides with Module 3. Mitigation: strict "structure not price" rule; price placeholders only; Optional items named but unpriced; the Margin-viable check stays a yes/no gate; a Note in 2.2.
2. **"Sales System" → sounding pushy, or any income implication:** Mitigation: frame outputs as *visibility and process*, respectful selling; no dollar examples; no projected revenue.
3. **Pipeline reads as "buy a CRM/app":** violates the no-app/no-portal scope. Mitigation: pipeline is a paper/spreadsheet tracker; explicitly tool-agnostic.
4. **Follow-Up Cadence sounds like spam/"chasing":** Mitigation: cadence = respectful, useful, timed; use `Follow-Up Cadence` (never "chasing"/"nurture").
5. **Offer Ladder tips into upsell hype:** Mitigation: ladder = clarity/fit, not pressure; Warning callout on hard-selling.
6. **Non-advice coverage:** any money-adjacent line needs a Note (Style Guide §9).

## 18. Repetition risks

1. **Re-teaching ideal customer / core offer** (already Module 1). Mitigation: reference the Snapshot; open 2.1 by pulling forward Module 1 outputs, not redefining them.
2. **Overlap with Module 4 (Weekly Operating Rhythm):** pipeline maintenance and the Weekly Close belong to Module 4. Mitigation: Module 2 *sets up* the pipeline and *hands* upkeep to Module 4 via forward reference; do not rebuild the rhythm.
3. **Overlap with Module 7 (Retention & Referrals):** following up **past customers** is Module 7; Module 2 follow-up is **active leads only.** Mitigation: state the boundary explicitly in 2.5.
4. **Overlap with Module 3:** offer packaging vs offer pricing — keep the seam clean (structure here, numbers there).
